# Quick Charge (QC)

ColorOS / RealmeUI 温控与充电策略改写模块。两条独立链路：

| 链路 | 做法 | 生效时机 | 恢复方式 |
|---|---|---|---|
| 配置改写 | 改写 `/vendor/etc` 下温控 XML、充电曲线、horae 配置的副本，bind mount 覆盖 | 开机早期，挂上即固定 | `umount`，重启自然恢复 |
| 温度伪装 | 守护进程周期性写 `thermal_zone*/emul_temp` 与 `/proc/shell-temp` | boot_completed 之后 | 卸载、`emul_temp` 归零 |

两条链路互不依赖：只挂配置也能降温控，只跑守护也能伪装读数。

- 模块 ID：`quickcharge`
- 数据目录：`/data/adb/quickcharge`
- 作者：[XiaohaoQvQ](https://github.com/XiaohaoQvQ)

---

## 快速开始

```sh
# 看状态
sh /data/adb/modules/quickcharge/action.sh status

# 开启温度伪装（默认参数：42℃ 以下满功率）
sh /data/adb/modules/quickcharge/action.sh temp static
```

安装后**默认只启用配置改写**，运行时伪装是关的（`temp_mode=off`）。
因为温度伪装会改变系统对温度的判断，装完先跑一次确认设备正常，再开伪装更稳妥。

在 Magisk / KSU 管理器里点模块的「操作」按钮，有终端时进入交互菜单。

## 默认策略

```
真实 30～38℃  →  上报 30℃     温差顶满 12℃
真实 39℃      →  上报 33℃
真实 40℃      →  上报 36℃
真实 41℃      →  上报 39℃
真实 ≥42℃     →  关闭模拟，系统读真实值自行降频
```

最后 4℃ 等步长爬升是必要的：从 30 直跳 42 会让系统看到壳温突变 12℃，反而触发一次额外降频。

## 参数

| 参数 | 默认 | 范围 | 作用 |
|---|---|---|---|
| `temp_mode` | `off` | `off` / `static` / `charge` | `static` 全程伪装；`charge` 只在充电且电量低于阈值时伪装 |
| `shell_temp` | 30 | 25～60 | 伪装基准温度（℃） |
| `aggr` | 10 | 0～10 | **温控档位**，越高越激进，可拉开温差 = 2 + 档位 |
| `wall` | 42 | 35～80 / `off` | 温度墙，真实温度到此即停止伪装 |
| `battery_limit` | 48 | 30～70 / `off` | 电池哨兵熔断阈值 |
| `sentinel_limit` | 85 | 60～110 / `off` | SoC/主板哨兵熔断阈值 |
| `curr_max` | 0 | 0～8000 | 充电限流（mA），0 = 不限 |
| `curve_offset` | 120 | 0～300 | 充电曲线温度轴右移量，0.1℃ 单位（120 = +12℃） |
| `fast_cap` | 55 | 20～90 | `charge` 模式生效的电量上限（%） |
| `power_scale` | 100 | 50～200 | 电流校准百分比，读数偏低/偏高时微调 |
| `tick` | 15 | 5～300 | 守护周期（秒）；`charge` 档固定 10 秒，不受此项影响 |
| `log_level` | 3 | 0～4 | 0 关 / 1 错误 / 2 警告 / 3 信息 / 4 调试 |

任一参数越界都会被拒绝，当前值保持不变，不会写进系统。

## 命令

```sh
sh action.sh status                 # 状态
sh action.sh temp static 32         # 开启伪装，基准 32℃
sh action.sh temp off               # 关闭伪装
sh action.sh gear 6                 # 温控档位降到 6（aggr 是旧名，仍可用）
sh action.sh wall 45                # 改成 45℃ 收手
sh action.sh hz 120                 # 写 120Hz（系统仍可按内容降频）
sh action.sh hz 144 hard            # 强制锁定 144Hz（不接受内容帧率切换）
sh action.sh hzguard off            # 关掉强制锁定，档位保留
sh action.sh hz off                 # 完全还原系统刷新率
sh action.sh pscale 110             # 电流读数偏低一成时校准
sh action.sh curr 3000              # 限流 3A
sh action.sh core 55                # CPU/GPU/DDR 固定报 55℃（独立于 temp 模式）
sh action.sh sentinel 90            # SoC 熔断改 90℃
sh action.sh level 4               # 调试日志
sh action.sh logs e 100             # 最近 100 条错误
sh action.sh logs boot              # 本次开机全过程
sh action.sh rebuild                # 重新生成覆盖层（一般不用，OTA 后开机自处理）
sh action.sh reset                  # 恢复初始状态
```

`logs` 的来源标记：`boot` / `mount` / `override` / `thermal` / `guard` / `charge` / `daemon` / `cmd`。

## WebUI

模块带 `webroot/index.html`，在 **KernelSU / KsuWebUI / MMRL** 里点模块的「打开」即可看到控制面板：

- 实时状态：真实温度、上报温度、挂载文件数、守护是否在跑
- **温控改写范围**三个按钮：全局运行 / 仅充电 / 关闭，点一下立即生效
- 温控档位 0～10（拖动即生效，显示对应温差）
- 温度墙 35～80℃，可单独关闭；关闭后伪装持续到熔断阈值前 2℃
- 基准温度 25～60℃
- 充电限流 0～8000mA、电池熔断 30～70℃、主板熔断 60～110℃
- 刷新率 90 / 120 / 144Hz，外加一个「强制锁定」开关，可一键还原
- 实时电流 / 功率曲线，只在页面打开时采样
- 重挂配置、重启守护

滑块松手才下发命令，避免拖动过程刷屏；参数走的是 `action.sh`，与命令行完全一致，改完立即生效，不需要重启。

### 温控改写范围

三个按钮对应 `temp_mode` 的三个取值，差别是**生效时机**，不是强度：

| 按钮 | 值 | 行为 |
|---|---|---|
| 全局运行 | `static` | 任何场景都改写：插电、拔电、游戏、待机都生效 |
| 仅充电 | `charge` | 插电时改写；拔电后 10 秒内还原，回到系统原温控 |
| 关闭 | `off` | 不写任何温控节点（覆盖层仍在，见下节） |

切到「仅充电」时会先看一次电源状态：没插电就立刻撤掉已写入的伪装，不等下一个 tick。
之后守护每 **10 秒**查一次电源状态，与 `tick` 无关——`tick` 调到 300 秒也是 10 秒，
拔电后最多 10 秒还原。这 10 秒一轮的成本可以忽略，因为 `sd_charge_tick` 不 fork。

### 「还原」还到哪一层

这里分两层，说清楚免得误解：

| 层 | 拔电后 |
|---|---|
| 传感器读数（`emul_temp` / `/proc/shell-temp`） | 归零，系统重新读到真实温度 |
| `/vendor/etc` 温控配置覆盖层 | 仍挂着，运行时不解挂 |

第二层是模块实现「满功率」的核心：把 `sys_thermal_control_config*.xml` 里的
`enable="true"` 改成 `false`，系统才不会在 42℃ 就降频限流。这些文件在 thermal HAL
启动时读一次，运行时解挂不会让已加载的策略失效，所以「拔电即还原」只能是传感器层。

要彻底回到原厂，卸载模块后重启。


## 模块简介显示当前状态

管理器（Magisk / KernelSU）模块列表里那一行简介是 `module.prop` 的 `description`。模块会在运行期把它改写成实时摘要：

```
QC · 温控档位 8/10 · 高刷 120Hz · 配置 9 项
```

三种模式写法不同：

| 状态 | 显示 |
|---|---|
| 全程伪装 | `QC · 温控档位 8/10 · 高刷 120Hz · 配置 9 项` |
| 开强制锁定 | `QC · 温控档位 8/10 · 高刷 120Hz 锁定 · 配置 9 项` |
| 仅充电 | `QC · 温控档位 8/10（仅充电）· 高刷关闭 · 配置 9 项` |
| 关闭 | `QC · 温度伪装关闭 · 高刷关闭 · 配置 9 项` |

改写时机：开机挂载完成、守护启动、切换模式、改参数、熔断。写入前先与上次内容比对，相同就不碰文件；只替换 `description` 一行，`id` / `version` 等逐字节保留。

两个已知限制：

- 管理器已经停在模块列表页时不会实时刷新，下拉或退出重进才会重新读取。
- 覆盖安装后、重启前，显示的是安装包里的静态文案（`QC · 欧加真温控与充电改写 …`）。

面板通过 KernelSU 的 `ksu.exec` 执行命令，纯静态页面、无外部依赖。Magisk 用户可装 KsuWebUI 独立应用加载。状态接口是 `sh action.sh json`，输出单行 JSON，也方便元模块或脚本消费。

**刷新率。** 面板上是「档位选择 + 强制锁定开关」，对应两种力度。

*普通档* 写系统 `peak_refresh_rate` 与 `min_refresh_rate`，和 ColorOS「屏幕刷新率」开关走同一路径，改完立即生效。开启前记下原值，关闭时原样写回；原本为空的键直接删除，交还系统默认。

*强制锁定* 在这个基础上多做两件事：把 `secure/match_content_frame_rate` 置 1（不接受内容帧率匹配），并让守护每 15 秒回读两个键，被系统改回就立即补写。视频播放时的 24/30fps 降频、静态画面下的降档，都能挡住。

### 为什么"锁定"不是绝对的

Android 的刷新率由 `DisplayModeDirector` 用固定优先级的**投票**决定，不是"谁后写谁赢"。高优先级会把低优先级的区间直接裁掉：

| 投票源 | 优先级 | 效果 |
|---|---|---|
| `min_refresh_rate` | 3 | 用户下限 |
| App `Window.setFrameRate` | 4 | 应用自报帧率 |
| `preferredDisplayModeId` | 5 | 应用指定模式 |
| `peak_refresh_rate` | 7 | 用户上限 |
| 省电模式 | 8 | 强制 `[0, 60]` |
| 皮肤温度 CRITICAL | 10 | 强制 `[0, 60]` |
| 屏下指纹解锁 | 12 | 成像期间锁帧 |

所以 `peak` / `min` 只能"表达偏好"。模块能做的只有两件事：把键写进去，并在被改回时补写。**下面三种场景挡不住**，面板会如实显示原因，而不是假装已锁定：

- **省电模式**（优先级 8）：`low_power=1` 时系统直接裁到 60Hz，写键无效。守护检测到后主动退让，面板显示「省电模式开启，锁定无效」。
- **皮肤温度过高**（优先级 10）：这是面板保护。硬顶等于拿屏幕寿命换帧率，模块不绕。
- **屏下指纹解锁瞬间**（优先级 12）：光学指纹要求固定帧率才能成像，持续几百毫秒，解锁完自动恢复。

还有一层：App 自己在 Surface 上设的帧率（优先级 4）是**逐层**的，SurfaceFlinger 会按活跃层选倍频。这一层要在 SurfaceFlinger 里改，超出 settings 的能力范围；能改的模块通常靠 hook，代价是黑屏与兼容性风险，本模块不做。

**连续三次写不回目标值就停手。** 继续每 15 秒和系统抢一次写，只会白耗 IO 并刷日志。此时守护记一条「已暂停补写（厂商锁定显示策略）」，面板显示 `drift`。

**代价。** 强制锁定会让 LTPO 面板失去降频省电的机会，功耗与发热都会上升；长时间高刷对 OLED 寿命也有影响。所以它默认关闭，开启时面板会二次确认。关闭后档位保留，只是把内容帧率策略交还系统。

**功耗。** `sh action.sh power` 读一次电池节点，返回 `ma` / `mv` / `w` / `temp` / `status` / `cells` / `src`。两条路径按顺序尝试：

1. **`/sys/class/oplus_chg/battery/bcc_parms`** —— 欧加真专属，逗号分隔 19 个字段，`[6]` 是电芯 0 电压、`[8]` 是电流、`[11]` 是电芯 1 电压，单位 mV / mA。
2. **`/sys/class/power_supply/battery/*`** —— 通用节点，电流自动识别 µA 与 mA，电压识别 µV 与 mV。

**双电芯为什么必须走第一条路。** 串联双电芯的总压是两颗相加（4.4 + 4.4 = 8.8V），但部分机型的 `voltage_now` 只报单芯电压。按 4.4V 算出来的功率正好少一半，30W 快充会显示成 15W。`bcc_parms` 里两路电压都在，相加才是真实总压；只有一路大于 1V 时才相加，单电芯机型这一位是 0。字段数不是 19 说明驱动版本不同、索引会错位，此时直接放弃这条路，不猜位置。

电流符号各平台约定相反，统一按 `status` 校正成「充电为正、放电为负」。读数仍有固定偏差的机型用 `pscale` 微调（百分比，50～200）。

面板每 3 秒采样一次，页面隐藏或关闭立即停止并清空，不写日志、不留后台进程。

> 双电芯读数的思路参考了 [PlusPlusBattery](https://github.com/dijia1124/PlusPlusBattery)（MIT），它把 `bcc_parms` 的字段位置和双芯相加的做法验证得很清楚。

## 安全设计

**哨兵隔离。** `battery` / `batt*` / `xo-therm` / `xtherm*` 永远不参与伪装，是整个系统里唯一可信的一路读数。把它们一起钉死会让充电 IC 失去温度反馈——这是"充着电死机"的主要来源。

**熔断。** 电池 48℃ / 其他传感器 85℃ 触发时，撤销全部伪装、模式置 `off`、`shell_temp` 清 0。两个阈值可分别关闭。

**渐进让步。** 上报值随真实温度抬高，距墙 4℃ 开始等步长爬升，到墙完全交还。任何分支下上报值都不超过真实温度——超过就成了伪造高温，系统会提前降频。

**参数校验。** 越界不截断到边界，而是拒绝：命令行入口直接报错、当前值不变（`temp` 命令例外，越界退到 30℃）。`state.conf` 里的损坏值在读取时回落默认，不会带着坏值去写节点。

**写入门槛。** 非 0 的目标温度必须落在 20～100℃，否则整次写入丢弃并记 `E` 日志。0 是合法值，语义为关闭模拟、交还真实读数，不是"上报 0℃"。

**开机自救。** 连续 3 次没走到 `service` 阶段就跳过挂载并清空清单。这是不依赖 recovery 的翻车出口。恢复：`sh action.sh reboot-safe` 或重启一次。

**回滚。** `mounts.list` 精确记录每个挂载点；清单丢失时按覆盖层目录反推，只卸确实出现在 `/proc/mounts` 里的路径。卸载后原文件逐字节恢复，`emul_temp` 归零，数据目录删除。

## 配置改写范围

只扫 `/vendor/etc`、`/odm/etc`、`/system/vendor/etc`、`/system/system_ext/etc`、`/vendor/qti/etc`（`-maxdepth 2`），只改这些文件：

| 文件 | 改动 |
|---|---|
| `sys_high_temp_protect_*.xml` | `true` → `false`，阈值不动 |
| `sys_thermal_control_config*.xml` | 开关属性 `true` → `false`，档位数据保留 |
| `thermallevel_to_fps.xml` | `fps` 全部改 144 |
| `sys_thermal_config.xml` | 含 `enable` 的行 `>1<` → `>0<` |
| `devices_config.json` | 充电温度窗口 `150,450]` → `150,550]` |
| `QEGA_Config.txt` | 取样节点 `xo-therm` → `battery` |
| `charging_*.txt` | 温度轴整体 +12℃（可调 `curve_offset`），上限截断 60℃ |
| `horae*.conf` | 置空（空文件比删除安全：SELinux 标签保留） |

**只改属性值，绝不删 XML 节点。** 删节点会留下无主闭标签，产出结构残缺的 XML，thermal HAL 解析失败 → 开机循环。

每个产物落地前校验：开闭标签必须配平、标签总数必须与原件一致、JSON 括号数一致。原件本身不配平则直接拒绝改写。不一致的产物丢弃，宁可不生效也不写坏文件。

OTA 后系统指纹（`ro.build.display.id` + 安全补丁）变化，`post-fs-data` 会自动解挂、重新生成、重新挂载，不需要手动干预。

## 已知限制

- **`curr_max` 只能限流，不能加速。** 充电功率由适配器、协议、电芯内阻决定，改上限无效。真正能提速的是让温度反馈变低（壳温伪装）。
- **温控档位在电池哨兵下会饱和。** 受 48℃ 熔断阈值约束，档位 `> 5` 在电池场景下可能达不到理论温差。
- **节点名因机型而异。** `shell-back` / `xo-therm` 这类名字不是所有机型都有；匹配不上时退化为"只挂配置"，日志里会有 `sentinel=none`。
- **SELinux。** `chcon --reference` 失败会汇总成一条 `W` 日志，接着尝试挂载。若系统服务仍拒绝访问，先查这条。
- **只骗得过读 `thermal_zone` 的软件层。** 内核级热保护、硬件断电保护不受影响，这是好事——它是最后一道防线。

## 性能

守护的每 tick 开销，在伪造 Android sysfs 的容器里跑 300 轮取均值。真机是
ARM + mksh，fork 更贵，实际约为下表 2～4 倍。

| 场景 | 每 tick CPU | fork |
|---|---|---|
| 温度伪装开启（默认） | 0.5 ms | 0 |
| 温度伪装关闭 | 0.2 ms | 0 |
| 仅充电时伪装 | 0.3 ms | 0 |
| 强制锁定 144Hz | 2.3 ms + 1 次 `settings` | 0 |

| 指标 | 数值 |
|---|---|
| 日均 CPU（默认档，tick=15s） | 约 3 秒 |
| 守护常驻内存 | 约 2.2MB |
| `post-fs-data` 冷启动（6 个配置文件） | 约 250ms |
| 停止响应（TERM → 退出） | 约 100ms，与 tick 无关 |
| 日志增长（稳定工况） | 约 96 行 / 天 |

四处关键优化：

1. **热路径零 fork。** 温度决策里所有取值改成「写全局变量」的版本，一次 tick
   不再产生二十多个子 shell。默认档从 5.6ms 降到 0.5ms，开销降低约 11 倍。
2. **`settings` 一次取两个键。** 锁定档原先每 tick 两次 `settings get`，真机上
   等于每 15 秒启动两个 `app_process`（单次 80～150ms）。改成一次
   `settings list system` 筛出两个键，进程数减半。
3. **日志只在变化时写。** 原先是固定每分钟一条，其中绝大多数是重复值；现在
   上报温度变化才记，另加 15 分钟兜底，稳定工况从 1440 行/天降到 96 行/天。
4. **温区表缓存。** `thermal_zone*/type` 只在启动时扫一次，之后每 40 tick 重扫；
   `emul_temp` 只在目标值变化时才写。

`sleep "$tick" & wait $!` 而不是直接 `sleep`：`wait` 是内建，收到 TERM 立刻响应，
不用等满一个 tick（最长 300 秒）。

想进一步降耗可以把 `tick` 调到 30 或 60 秒，代价是参数生效延迟变长：
改完参数靠 SIGUSR1 立即唤醒，所以只影响「系统自己变了」这类被动场景的响应。

## 目录结构

```
quickcharge/
├── module.prop
├── customize.sh        安装：设备检测、生成覆盖层、初始化参数
├── post-fs-data.sh     开机早期：挂载覆盖层，OTA 后自动重建
├── service.sh          开机后期 + 守护进程（--daemon）
├── action.sh           控制入口：CLI + 交互菜单
├── uninstall.sh        卸载：停守护、卸挂载、归零、清数据
├── lib/qc.sh           核心库：配置改写 / 温度伪装 / 充电，单文件
└── META-INF/...
```

`files/` 是安装时生成的覆盖层（不在包里），存放改写后的配置副本，再 bind mount 到系统分区。
如果模块目录只读（元模块放在只读分区），自动回落到 `/data/adb/quickcharge/overrides`。

## 卸载

在管理器里卸载即可。卸载脚本会停守护、卸全部挂载、把 `emul_temp` 写 0、删除数据目录。

想先手动确认：

```sh
sh /data/adb/modules/quickcharge/action.sh umount   # 只卸配置覆盖
grep -c thermal_zone /proc/mounts                   # 应为 0
```

卸载后重启一次最干净。
